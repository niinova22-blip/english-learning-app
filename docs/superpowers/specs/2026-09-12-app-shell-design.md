# App Shell — Design Spec

Date: 2026-09-12
Status: Approved for implementation planning
Slice: 2 of N (follows the learning-engine slice; see that slice's spec
for the full future-slices list)

## Context

Slice 1 built `LearningEngine` — a UI-free Swift Package with a real
FSRS-6 scheduler, a SwiftData content model, an i+1 calculator, and an
interleaving session builder, verified via GitHub Actions macOS CI
since local dev happens on Windows. This slice wraps that engine in a
minimal, real (not stubbed) SwiftUI app so it can actually be used and
seen — on the user's iPhone 11, sideloaded via AltServer/AltStore since
neither a Mac nor a paid Apple Developer account is available.

## Goals

- An Xcode project (generated by XcodeGen from a checked-in
  `project.yml`, not hand-written or committed as `.xcodeproj`)
  containing one iOS app target, depending on `LearningEngine` as a
  local Swift package.
- A "Today" screen that builds a real daily session via
  `DailySessionBuilder` against the seeded `SampleContent` package,
  presents items one at a time, and records ratings through
  `FSRSStateStore` into a real (not in-memory) SwiftData store.
- A session-complete summary screen.
- A second, minimal screen (Settings/About) — enough to prove
  multi-screen navigation works, not a real settings surface yet.
- A device-generated UUID standing in for a user id (no auth system
  yet).
- CI: every push verifies the app target actually builds (XcodeGen +
  `xcodebuild`, unsigned); a manually-triggered workflow produces an
  unsigned `.ipa` artifact for AltStore sideloading onto the test
  iPhone.

## Non-goals (deferred, per the learning-engine spec's future-slices list)

- Freemium/premium gating, ads, subscriptions
- Real content authoring / LLM-generated content
- Local on-device LLM tutoring or conversation
- Speech/pronunciation
- Any real account/auth system
- Code signing for App Store distribution — this slice ships an
  unsigned build; AltServer performs its own signing at install time
  using the user's free Apple ID, which is the whole reason that path
  exists.

## Architecture

A new `App/` directory at the repo root, sibling to `LearningEngine/`:

```
App/
  project.yml          # XcodeGen spec — generates App.xcodeproj, gitignored
  Sources/EnglishApp/
    EnglishAppApp.swift        # @main, ModelContainer setup, seeding
    Today/
      TodayView.swift
      TodaySessionCoordinator.swift   # plain-Swift session logic, unit-testable
    Settings/
      SettingsView.swift
  Tests/EnglishAppTests/
    TodaySessionCoordinatorTests.swift
```

`project.yml` declares one iOS app target (deployment target iOS 17,
matching `LearningEngine`'s platform floor) with a local Swift package
dependency on `../LearningEngine`. `App.xcodeproj` itself is
`.gitignore`d — CI (and any future dev with a Mac) regenerates it from
`project.yml` via `xcodegen generate` before building. This keeps the
one genuinely diffable, human-editable source of truth in git instead
of a generated `.pbxproj`.

**Design-for-isolation choice:** view-layer code (`TodayView.swift`)
stays thin — it renders state and forwards taps. The actual logic of
"which session to build right now" and "how to compute the current
`UserLevelSnapshot`" lives in `TodaySessionCoordinator`, a plain Swift
type with no SwiftUI import, constructible with a `ModelContext` and
`userID`. This mirrors `LearningEngine`'s own UI-free design and means
the one piece of real logic in this slice is unit-testable via the
same `scripts/ci-test.sh`-style CI verification, not something only
checkable by eye on a phone.

## Data model & seeding

The app owns one persistent `ModelContainer` for the full
`LearningEngine` schema (`ContentPackage`, `Unit`, `Lesson`,
`LearningItem`, `ItemContent`, `ReviewLog`, `UserItemState`),
constructed once in `EnglishAppApp.swift` and injected via
`.modelContainer(...)`. On first launch (detected by an empty
`ContentPackage` fetch), the app inserts
`SampleContent.ydsStarterPackage()` into the context so there's
real content to review from the very first run.

## User identity (stand-in)

A `UUID` generated once and persisted in `UserDefaults`
(`"userID"`) stands in for a real account. `TodaySessionCoordinator`
and every `FSRSStateStore` call use this value. When a real
account/auth system arrives in a later slice, this becomes a
migration, not a redesign — every persisted row is already keyed by
`userID` string.

## Today flow

1. `TodaySessionCoordinator.buildTodaySession()`:
   - Fetches all `LearningItem`s from the seeded package.
   - Fetches this user's `UserItemState` rows to find due items.
   - Computes a `UserLevelSnapshot`: cold-start (per
     `ComprehensibleInputCalculator`'s existing cold-start handling) if
     the user has no `ReviewLog` history yet; otherwise
     `rollingComprehensionAccuracy` is the fraction of `.good`/`.easy`
     ratings among the last 20 `ReviewLog` rows for this user.
     `knownItemIDs` is left empty for v1 (per the learning-engine
     spec's own documented scope for the i+1 calculator, which doesn't
     consume it yet either).
   - Calls `DailySessionBuilder().buildSession(...)` with
     `phase: .fullInterleaving` (the phase state machine described in
     the original product notes — tracking days since a topic was
     introduced to progress blocked → hybrid → full — doesn't exist
     yet; starting everyone at full interleaving is the honest v1
     default, not a silent gap) and `sessionSize: 10`.
2. `TodayView` shows one item at a time: headword/prompt, a "Show
   Answer" tap reveals definition + example sentences + translation,
   then four rating buttons (Again/Hard/Good/Easy) call
   `FSRSStateStore.recordReview` and advance to the next item.
3. When the queue empties, navigate to a summary screen showing the
   count reviewed, with a button back to Today (which will show
   "nothing due" until tomorrow, or can be relaunched for another
   round — no daily lockout in v1).

## Settings/About screen

Minimal: shows `learningEngineVersion` (already exported by the
package) and app version. Includes a "Reset local data" action that
deletes the SwiftData store — a deliberate dev convenience for
repeated testing during this early phase, not a real user-facing
feature; it can be removed or gated later.

## CI changes

- A new job (either in the existing workflow or a new
  `.github/workflows/app-build.yml`) that, on every push: installs
  XcodeGen (`brew install xcodegen` — the GitHub-hosted macOS runner
  already has Xcode and Homebrew), runs `xcodegen generate` inside
  `App/`, then `xcodebuild build -project App.xcodeproj -scheme
  EnglishApp -destination 'generic/platform=iOS'
  CODE_SIGNING_ALLOWED=NO`. This is a build-only gate (does the app
  target actually compile against the current `LearningEngine`), not a
  UI test — there is no automated UI verification in this slice; the
  user verifies on their own device via AltStore.
- A `workflow_dispatch`-triggered job that builds an unsigned `.ipa`
  (zip of `Payload/EnglishApp.app`) and uploads it as a workflow
  artifact, for the user to download and sideload via AltServer.
  **Open question the plan must resolve empirically:** whether
  AltServer can re-sign a fully unsigned `.app` packaged this way, or
  whether it needs a specific ad-hoc export step first — this is a
  known unknown, not a designed-away one, and the plan should treat
  the first real sideload attempt as a validation step rather than
  assuming success.

## Testing

- `TodaySessionCoordinatorTests` (XCTest, run via `scripts/ci-test.sh`
  the same way `LearningEngine`'s tests are): covers the snapshot
  computation (cold-start vs. rolling-accuracy cases) and that
  `buildTodaySession()` returns a non-empty, size-capped list against
  seeded sample data.
- No automated UI tests in this slice. Manual verification is the
  user, on their iPhone, via the sideloaded build.

## Future slices this unblocks

Once this ships, the next natural slices (content generation, local
LLM tutoring, freemium gating) all have a real screen to plug into
instead of a vacuum.
